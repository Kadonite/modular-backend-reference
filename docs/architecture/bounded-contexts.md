# Bounded Contexts

## 1. Purpose

This document defines the initial bounded contexts within Modular Backend Reference.

Each bounded context represents a distinct business capability with its own domain model, responsibilities, and rules.

The objective is to establish clear ownership of business behaviour and data while minimising coupling between modules.

## 2. Context Overview

The initial system consists of six bounded contexts.

| Bounded Context | Primary Responsibility |
|---|---|
| Identity | User identity and account management |
| Character | Character creation and progression |
| Inventory | Item ownership and storage |
| Economy | Currency and financial transactions |
| Crafting | Material processing and production |
| Notifications | Notification delivery |

## 3. Identity

### Responsibility

Manage user identity and account-related capabilities.

### Core Concepts

- User
- Account
- UserIdentity
- AccountStatus

### Owns

- User account records.
- Account lifecycle.
- Identity-related business rules.

### Does Not Own

- Character progression.
- Inventory contents.
- Financial transactions.

### External Interactions

Other contexts may consume identity information through explicit application contracts.

Authentication and authorisation infrastructure may be provided by Laravel, but domain-level account rules remain within Identity.

## 4. Character

### Responsibility

Manage the creation, identity, and progression of characters.

### Core Concepts

- Character
- CharacterId
- CharacterName
- CharacterLevel
- CharacterStatus

### Owns

- Character identity.
- Character lifecycle.
- Character progression rules.
- Character-specific attributes.

### Does Not Own

- User authentication.
- Inventory persistence.
- Currency balances.
- Crafting recipes.

### External Interactions

Character creation requires an existing account identity.

Inventory may associate an inventory owner with a character identifier without directly accessing Character's internal repository.

## 5. Inventory

### Responsibility

Manage ownership, storage, and movement of items.

### Core Concepts

- Inventory
- InventoryId
- InventoryItem
- ItemDefinition
- ItemId
- ItemQuantity
- ItemOwnership

### Owns

- Inventory contents.
- Item ownership records.
- Inventory capacity rules.
- Item movement and transfer rules.

### Does Not Own

- Item purchasing prices.
- Currency balances.
- Crafting recipes.
- Character progression.

### External Interactions

Inventory may receive item grants from other contexts through explicit application contracts.

Transfers and other inventory mutations must enforce ownership and capacity invariants.

## 6. Economy

### Responsibility

Manage financial transactions and economic operations.

### Core Concepts

- Wallet
- WalletId
- Currency
- CurrencyAmount
- Transaction
- TransactionId
- Trade

### Owns

- Wallet balances.
- Currency movements.
- Transaction history.
- Economic transaction rules.

### Does Not Own

- Inventory storage.
- Item definitions.
- Character progression.
- Crafting recipes.

### External Interactions

Economy may interact with Inventory through explicit contracts when a financial transaction requires an item transfer.

Financial operations must protect against duplicate processing and inconsistent balances.

## 7. Crafting

### Responsibility

Manage recipes, material requirements, and production workflows.

### Core Concepts

- Recipe
- RecipeId
- CraftingJob
- CraftingJobId
- MaterialRequirement
- CraftingResult

### Owns

- Recipe definitions.
- Crafting requirements.
- Crafting job lifecycle.
- Production rules.

### Does Not Own

- Inventory storage.
- Item ownership.
- Currency balances.
- Character identity.

### External Interactions

Crafting coordinates with Inventory to consume required materials and grant produced items.

These operations require carefully defined consistency and failure-handling rules.

## 8. Notifications

### Responsibility

Manage the delivery of notifications generated by application activity.

### Core Concepts

- Notification
- NotificationId
- NotificationRecipient
- NotificationChannel
- NotificationStatus

### Owns

- Notification records.
- Delivery status.
- Notification delivery preferences.
- Delivery attempts.

### Does Not Own

- Business rules belonging to other contexts.
- The lifecycle of characters or accounts.
- Financial transaction state.

### External Interactions

Notifications consumes explicitly published events or application requests from other contexts.

It should not directly access the internal repositories of other modules.

## 9. Module Communication

Modules should communicate through explicit contracts.

The initial implementation should favour synchronous application-level contracts when immediate results are required.

Asynchronous integration events should be introduced when workflows benefit from decoupling or eventual consistency.

Examples:

| Source | Destination | Interaction |
|---|---|---|
| Identity | Character | Account identity verification |
| Character | Inventory | Inventory association |
| Crafting | Inventory | Consume materials and grant results |
| Economy | Inventory | Coordinate item purchases and transfers |
| Inventory | Notifications | Publish item transfer notification |
| Economy | Notifications | Publish transaction notification |

These interactions describe business capabilities, not permission for one module to access another module's internal implementation.

## 10. Dependency Rules

The following rules should guide implementation:

1. Each module owns its domain model.
2. Modules must not access another module's internal repositories.
3. Modules must not depend on another module's infrastructure implementation.
4. Cross-module interactions must use explicit contracts.
5. Domain models should not contain dependencies on Laravel.
6. Shared abstractions must represent genuinely common concepts.
7. Circular module dependencies are not permitted.

## 11. Data Ownership

Each bounded context is responsible for its own business data.

The initial deployment may use a shared PostgreSQL database, but logical ownership must remain explicit.

Modules should not bypass their public contracts by querying another module's tables directly.

The physical database structure should not be mistaken for the logical domain boundaries.

## 12. Future Considerations

These boundaries are initial design hypotheses.

They should be revisited when implementation reveals:

- Overlapping business responsibilities.
- Excessive cross-module communication.
- Unclear data ownership.
- Difficult transaction boundaries.
- Unnecessary abstractions.
- Strong reasons to separate or combine capabilities.

Significant changes should be recorded in Architecture Decision Records.
